# LivePDF — Phase 10.6: PDF Redlining (Track Changes for PDFs)

Phase 10 gave LivePDF comments, threads, and formal approvals — but a comment is just talk. It tells the owner something is wrong; it doesn't say exactly what the fix should be. Phase 10.6 closes that gap. It adds redlining — the ability for a reviewer to propose an actual replacement or deletion for a specific piece of text, right on the PDF, and for the owner to accept or reject each proposal one at a time. Accepted proposals are then baked into a brand-new version of the document automatically. This is the difference between a reviewer saying "this clause is unclear" in a comment, and a reviewer saying exactly what the clause should say instead — and the owner being able to accept that exact wording with one click. It is what lawyers, editors, and contract teams actually expect from a serious document tool, because it is the PDF equivalent of Track Changes in Word.

1. What a redline proposal actually means
A redline is not a comment. A comment floats near a piece of text and talks about it. A redline replaces or removes the text itself, but only as a proposal — nothing changes on the actual PDF until the document owner explicitly approves it. When a reviewer drags their cursor across a sentence or phrase on the PDF, a small popup appears offering two choices: suggest a replacement, or suggest a deletion. If they choose replacement, they type what the text should say instead. If they choose deletion, they just confirm. Either way, nothing is altered yet — a proposal record is created and sits in a pending state until the owner acts on it. This is the same mental model as Word's Track Changes: the original author sees every suggested edit, and decides, one by one, whether to keep it.

2. How the exact text position is captured
The hard part of redlining is the same hard part as inline comments in Phase 10 — knowing precisely which words on the page are being talked about. When the reviewer selects text, you're not just grabbing the string they highlighted; you're grabbing its bounding box on the page, in PDF point coordinates, using the exact same pixel-to-point conversion the diff engine from Phase 6 and the comment anchors from Phase 10 already use. You store the page number and the box's x, y, width, and height in PDF points, not screen pixels, so the proposal stays attached to the right words no matter what zoom level someone is looking at the page in later.

3. Redline data model
Each proposal has an ID, the document it belongs to, the version it was made against, the ID of the reviewer who proposed it, the page number, the anchor box in PDF points, the original text that was selected, and the proposed replacement text — which is left empty when the proposal is a deletion rather than a replacement. It also has a status that starts as pending and moves to either accepted or rejected once the owner decides, and eventually to applied once an accepted proposal has actually been baked into a new version. Timestamps record when it was created, when it was decided, and when it was applied. Unlike comments, a proposal has no threading — it's a single suggestion, not a conversation, though nothing stops a reviewer from also leaving a comment nearby to explain their reasoning.

4. What the owner sees
When the document owner opens the PDF, every pending or accepted proposal shows up as a coloured underline directly beneath the affected text — red for a suggested deletion, blue for a suggested replacement — the exact same overlay technique used for comment markers and diff highlights in earlier phases. Alongside the PDF, a proposals panel lists every suggestion with the reviewer's name, the original wording, and what they're proposing instead. This is deliberately visual and side-by-side, the same way Word shows strikethrough and inserted text together, so the owner never has to imagine what the change would look like — they can see both versions at once before deciding.

5. Accepting and rejecting proposals
For every proposal in the panel, the owner has two buttons: Accept and Reject. Rejecting simply dismisses it — the underline disappears from the PDF, though the proposal record itself stays in the database rather than being deleted, so there's a permanent trail of what was suggested and turned down. Accepting doesn't change the PDF immediately. It just marks the proposal as ready to be incorporated, the same way checking a box in Word's Track Changes review pane doesn't rewrite the document until you actually apply it. This separation — decide now, apply later — lets an owner go through dozens of proposals from multiple reviewers and make all their decisions before committing to a single new version, rather than generating a new file after every individual click.

6. Applying accepted changes
Once the owner is done deciding, a single "Apply accepted changes" button triggers the real work. Every proposal marked accepted is sent to the Python microservice, which opens the current PDF, finds each proposal's text using its stored bounding box, redacts the original text, and — if it's a replacement rather than a deletion — writes in the new text at the same position. This is the same PyMuPDF toolkit already installed and used by Phase 6's diff engine, just used to edit rather than compare. The result is uploaded as a new version, exactly like any owner-initiated upload in Phase 2, and every applied proposal is marked as such so it's clear which version first contained that change.

7. The diff engine finishes the story
The moment the new version exists, Phase 6's diff engine runs on it automatically, comparing it against the version just before it. This means the owner — and anyone else looking at the document — doesn't just see that a new version exists; they see exactly which sentences changed, highlighted the same way any other version-to-version diff is highlighted elsewhere in LivePDF. Redlining and diffing were built to work together: one captures a reviewer's intent, the other confirms and displays the actual outcome.

8. Who's allowed to propose changes
Redlining rides on the same permission system as commenting from Phase 10 rather than introducing a new one. If a share link has "Allow comments" turned on, the people using that link can also propose redlines — the two are treated as one reviewing privilege, not two separate toggles the owner has to manage. Only the document owner can accept, reject, or apply proposals, regardless of who created them, since applying changes actually rewrites the document that everyone else is viewing.

9. Redlining during a formal review
Because Phase 10 already has a formal approval workflow with its own five states, redlining is deliberately blocked from applying changes while a document is sitting in Pending Review. Reviewers can still propose redlines during that time — that's often exactly when they're looking closely enough to catch wording issues — but the owner can't apply them until the review round has concluded, so a document's content can't shift out from under a reviewer who is actively deciding whether to approve it.

10. What happens to text that doesn't fit
This is the one place where the illusion of "editing a PDF" runs into what a PDF actually is. A PDF has no paragraph flow — text sits at fixed coordinates, and there's no way to reflow a page the way a word processor would if a sentence gets three words longer. If a reviewer proposes a replacement that's roughly the same length as the original, the result looks clean. If it's dramatically longer or shorter, the new text can overlap what's next to it or leave an odd gap, because there's simply nowhere else on a fixed page for extra characters to go. Rather than pretend this isn't a limitation, the UI says so directly when someone is typing a much longer replacement, and the fix for a genuinely reflow-heavy edit is the separate, larger Phase 13.5 feature — real-time collaborative editing at the source-document level — not something 10.6 tries to solve.

11. Every decision is on the record
Every proposal's full lifecycle — created, accepted, rejected, applied — is written to the same audit_logs table introduced in Phase 1 and already used by comments and approvals in Phase 10. Nothing about a redline is ever silently lost: a rejected suggestion stays visible in the history even though it never touched the document, and an applied one is traceable to the exact version it produced. For the legal and compliance teams this feature is really built for, that permanent record of who suggested what, who approved it, and which version it landed in is often the entire point.
